★★★ 链 1 · MySQL 索引为什么用 B+ 树，不用哈希 / 红黑树 / B 树？

一层：哈希索引只支持等值查询，范围、排序、模糊全废；红黑树是二叉树，数据量大了树太高，每层一次磁盘 IO 扛不住；B 树非叶子节点也存数据，单页能放的索引项少；B+ 树非叶子只存"键 + 页指针"，单页扇出大 → 树矮胖（千万级只要 3 层），且叶子节点是双向链表，天然支持范围查询和排序。

追问①：3 层 B+ 树到底能存多少行？算给我看。
页大小 16K；非叶子页一个"键 + 指针"约 14 字节（bigint 8B + 指针 6B），单页扇出约 1170；叶子页按每行 1K 算存 16 行 → 1170 × 1170 × 16 ≈ 两千两百万行。且根节点常驻内存，实际磁盘 IO 只有 1-2 次。——能算出这个数字的人，全场面试不超过三个。

追问②：为什么所有规范都强制自增主键？用 UUID 会怎样？
一句话：聚簇索引的数据按主键顺序存放，插入位置由主键决定。自增 = 永远追加到最右页：写满就申请新页、旧页不动、写盘是顺序写。UUID = 插进中间的随机页，引发三步灾难：① 页分裂——目标页满了要劈：申请新页、搬走一半行、改链表、父页加指针（父页满了级联再劈）；② 页碎片——一个满页变两个半满页，长期下来叶子页平均只装五六成满：表膨胀、范围扫描读更多页、buffer pool 一半装空气；③ 随机 IO——目标页随机 → 大概率不在 buffer pool，先随机读进内存再随机写回；磁盘层面从文件末尾追加写变成散布全文件的随机写。外加扇出那一刀：UUID 36 字节 → 扇出从 ~1170 掉到 ~390（见地基节），树更高；且二级索引叶子存主键值，每一棵二级索引都跟着变大。再追一层（防身）：非唯一二级索引的随机写入，InnoDB 有 change buffer 缓解——修改先缓存，页被读进内存时再合并（45 讲第 9 讲）。

追问③：联合索引 (a,b,c)，where b=? 走不走索引？where a=? and b>? and c=? 呢？
前者不走——索引内部是先按 a 排、a 相同再按 b 排，没有 a，b 在整棵树里无序，只能全扫（MySQL 5.6+ 可能走 ICP 索引下推做引擎层过滤，但那不是"用索引定位"）。后者：c 用不上——b 是范围条件，b 之后 c 无序。口诀：范围之后全断。——底层原理（字典序元组 + 完整断点清单 + key_len 验证法）见地基⑤。

追问④：自增主键暴露出去，竞品不就能算出你的业务量吗？
这叫德国坦克问题——竞品隔一周下两单，订单号一减就是你这周的单量。正解不是"不用自增主键"，而是分层：自增主键当里子，业务编号当面子。① 物理主键照旧自增 bigint（阿里规约强制：表必备 id unsigned bigint、单表自增）——吃满聚簇索引收益，且永不离开数据库；② 对外暴露的业务编号用"全局唯一 + 趋势递增 + 不含业务量"的方案：雪花 ID / 有序 UUID（8.0 的 uuid_to_bin(@uuid, true)）/ 淘宝式"时间 + 去重字段 + 用户尾号"（真实订单号 19 位、前 14 位单调递增）；③ 小系统偷懒路线：内部自增 + 出站混淆（Feistel 加密 / Hashids）。面试组合拳："自增主键只做物理主键，对外业务编号趋势递增但不含业务量——前者保 B+ 树插入性能，后者防德国坦克问题。"

★★★ 链 1 补充 · MySQL 有哪些类型的索引？（先分维度再枚举）

答法骨架："分三个维度——按物理存储、按逻辑用途、按数据结构。"先给骨架再展开，结构化本身就是分。

① 按物理存储（InnoDB 最核心）：聚簇索引叶子存整行，一张表只有一棵（数据只能按一种顺序物理存放），就是主键那棵 B+ 树——字典的正文，目录和内容长在一起；二级索引叶子存"索引列 + 主键值"，可以很多棵，查整行要回表——部首检字表查到的只是页码，还得翻回正文。没主键时 InnoDB 选第一个非空唯一索引顶上，都没有就生成 6 字节隐藏 row_id——这就是"表必须有主键"的底层原因。对照组：MyISAM 没有聚簇索引，叶子存数据行的磁盘地址，次次回表——聚簇 = 数据跟着索引走。

② 按逻辑用途：主键 / 唯一（允许 NULL；接链 5：等值命中时 next-key 退化为记录锁，并发更高）/ 普通 / 联合（最左前缀说的就是它）/ 前缀（长字符串只索引前 N 字符，省空间但不能用于排序）。注意：覆盖索引不是类型，是用法——查询列全在索引里就免回表（接链 2）。

③ 按数据结构：B+ 树默认全能（本课全部地基）；哈希——Memory 引擎默认，等值 O(1) 范围全废，InnoDB 还有个不可控的自适应哈希索引 AHI（热点页自动建哈希，提一嘴是加分）；全文 FULLTEXT——倒排思路（词 → 文档列表），5.6 起 InnoDB 支持，5.7.6 内置 ngram 才真正支持中文；空间 R-Tree——地理位置 GIS，5.7 起。

④ 版本线（证明你用的是 2026 年的 MySQL）：5.6 → ICP 索引下推（链 1 追问③那个）；5.7 → 生成列（给生成列建索引 = 变相函数索引）；8.0 → 真正的降序索引（5.7 写了语法会被悄悄忽略）、不可见索引（想删索引又怕出事？先设 invisible 观察一阵 = 影子删除）、函数索引（8.0.13，"列上套函数索引失效"这条有了官方解法）、多值索引（8.0.17，给 JSON 数组建）。

你的实战锚点：慢 SQL 整改经历 + "下线索引前先设 invisible 观察"——把 8.0 新特性和你的真实治理动作绑在一起讲，非常像干过活的。

★★★ 链 2 · 什么是回表？怎么避免？

一层：二级索引的叶子节点只存"索引列 + 主键值"。查到之后还要拿主键去聚簇索引把整行捞出来——这一趟额外的查找叫回表。

追问①：什么是覆盖索引？
查询要的所有列都在索引里，不用回表，explain 的 Extra 显示 Using index。实战动作：高频查询把返回列设计进联合索引。但补一句权衡：索引越宽，写入维护成本和回表收益要一起算——这句话出口，面试官知道你不是背书的。

追问②：select count(*) 走什么索引？InnoDB 为什么不缓存总行数？
优化器会选最小的那棵二级索引扫（页数少、更便宜）。不缓存行数是因为 MVCC——同一时刻不同事务"可见的行数"不一样，缓存没有定义。对比：MyISAM 没事务，所以可以缓存。

你的实战锚点：话费充值平台 TPS 500 的订单查询——哪些查询走覆盖索引、哪些必须回表，讲链 3 整改故事时顺手带上。

★★★ 链 2 补充 · 业务键不暴露后，C 端查询是不是必然回表？

先纠一个概念：覆盖索引 ≠ "走主键查询"。它的定义是"SELECT 的列全在你用的那棵索引里 → 免回表"，和用哪个键查无关——select status, amount from orders where order_no=? 配上索引 (order_no, status, amount) 照样覆盖。

单行回表的成本账：select * where order_no=? 确实回表，但多走的聚簇树 3 层里根和第二层常驻 buffer pool，实际多约 1 次页访问 ≈ 微秒级——用微秒换业务量不泄露，全行业都这么选。回表真正的灾难是范围查询命中几万行、每行回表一次（随机 IO 风暴）——这也是优化器"回表比例太高干脆全表扫"的原因。

按查询形态分开处理：① 详情页（where order_no=? 单行）——接受回表，没人优化这个；② 列表页（C 端"我的订单"，条件其实是 user_id）——联合索引把"过滤列 + 展示列"包进去（如 user_id, status, amount, create_time），覆盖索引免回表；③ 极端场景——趋势递增的业务号直接当聚簇主键（淘宝订单号形态），业务键查询 = 聚簇查询零回表，代价是业务字段与物理存储耦合。

30 秒面试版："物理主键自增但不外露，对外业务编号走唯一二级索引。单行查询回表是微秒级，可忽略；列表查询用覆盖索引把展示列包进索引，免回表；极端场景才把趋势递增的业务号当聚簇主键。"

★★★ 链 2 补充 · JOIN 一定会回表吗？小表驱动大表是什么原理？

JOIN 里的回表发生在哪：JOIN = 嵌套循环（NLJ），驱动表每行 → 去被驱动表查一次。被驱动表用主键关联（eq_ref）= 直接走聚簇索引拿整行，没有回表概念；用二级索引关联时，判定规则和单表一样——要的列在索引里就覆盖，不在才回表。JOIN 里写 select * 是自杀行为。

小表驱动大表（成本公式）：总成本 ≈ 驱动表过滤后行数 × 被驱动表单次查询成本。被驱动表关联字段有索引时，单次成本是一次 3 层树查找、与表多大无关，所以让过滤后行数少的表当驱动——注意是"过滤后行数少"，不是物理表小：1000 万行的表过滤到 100 行，它就是"小表"。

没索引时规则不变、原因变了：无索引走 BNL——驱动表装进 join buffer，扫被驱动表在内存逐行比对，小表当驱动是为了 buffer 装得下（装不下要分段重扫大表）；8.0.18+ 等值 JOIN 默认 Hash Join，同样是小表进内存建哈希。有索引为循环次数，无索引为内存占用，别混着背。

真要回整行时的四层武器：① MRR / BKA（5.6+）：二级索引查出一批主键先排序再回表，随机 IO 变近似顺序 IO——次数没变，每次都便宜；② 延迟关联（链 3 深分页同款）：先覆盖索引翻页拿 ID，再回表取这一页详情——回表次数从 N 压到一页大小；③ 执行顺序：小表驱动 + Hash Join；④ 架构层：要 join 四张表、每张十几列还带模糊搜的列表查询，正确答案是搬出 MySQL（ES / 读模型），不是硬刚。

谁决定驱动顺序：优化器按统计信息自动选，explain 第一行就是驱动表；选错了（统计过期常见）先 analyze table，还不行用 straight_join 强制（慎用，写死不自适应）。口诀收拢：回表优化只有两条路——减少回表次数，或让每次回表更便宜；都走不通，说明这个查询不该在 OLTP 里跑。

★★★ 链 3 · 线上接口慢了，怀疑是 SQL，你的排查路径？

一层：四步走：① 慢查询日志（long_query_time）+ 监控定位到具体 SQL；② explain 看执行计划——type 至少到 range（ALL = 全表扫描，立刻报警）、key 是实际走的索引、rows 是扫描行数、Extra 警惕 Using filesort / Using temporary；③ 对症下药：缺索引补索引、改写 SQL（拆复杂 JOIN / 覆盖索引 / 延迟关联）、热点上缓存；④ 验证：对比优化前后 rows 和耗时，灰度观察。"定位 → 量化 → 对症 → 验证"这八个字是骨架，先说骨架再展开。

追问①：深分页 limit 1000000, 10 为什么慢？怎么优化？
要扫出前 100 万 + 10 行再丢掉前 100 万。两种改法：游标式 where id > 上页最大id limit 10（聚簇索引范围扫，最快）；或延迟关联——先用覆盖索引只查出 10 个 id，再回表取整行。

追问②：明明有索引，explain 却没走，有哪些可能？
失效清单一口气背：列上做函数或运算；隐式类型转换（varchar 列传了数字）；like 前导 %；OR 两边不都有索引；不满足最左前缀；优化器估算全表反而更快（表太小 / 回表比例太高）。最后一项的解法：analyze table 更新统计信息，或 force index 强制验证。

你的实战锚点（王牌，讲完链路主动带）："我在嘉立创做过一轮慢 SQL 集中整改——复杂 SQL 拆分 + 索引调整 + 热点上缓存。"今晚把这个故事的三件事各回忆一个具体例子：哪张表、什么现象、改完快了多少。

★★★ 链 3 补充 · EXPLAIN 输出怎么逐列解读？（拿美团真实执行计划练手）

四看法（别逐列背）：① id 看执行顺序——id 大的先执行，id 相同从上往下，NULL（union result）最后；<derived2> 的意思是"id=2 的查询造出来的临时表"。② type 看访问方式——system > const > eq_ref > ref > range > index > ALL，至少 range，见 ALL 报警；eq_ref = 主键等值关联（一次一行），ref = 非唯一索引等值。③ key / key_len / ref 看索引用量——possible_keys 是候选、key 是实际选中（NULL = 没用索引）；key_len 是进访问路径的字节数（地基⑤ 的断点验证器）；ref 是索引列在和谁比（const 常量 / 前表列）。④ rows + Extra 看成本——rows 是预估扫描行数，"绝大部分 rows 小的语句执行一定很快"（美团原话），优化 SQL 很大程度就是优化 rows；Extra 警惕 Using filesort / Using temporary，加分 Using index（覆盖免回表）/ Using index condition（ICP）。

练手一（stage_poi 的真实执行计划）：type: ALL | key: NULL | rows: 3613155 → 翻译：全表扫 361 万行只为找 951 行——病不在 SQL 写法，在没有可用索引。

查询执行顺序（两层答案都备着）：① 逻辑顺序（子句求值次序）：FROM/JOIN → ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT——解释了 WHERE 为什么不能用 SELECT 的别名；② 物理顺序（MySQL 怎么跑）：连接器 → 分析器 → 优化器（EXPLAIN 展示的就是它的产出） → 执行器调引擎逐行取数，多表 JOIN 走嵌套循环、EXPLAIN 第一行就是驱动表（地基①）。

stage_poi 案例复盘：两个低区分度字段凭什么联合索引就解决了？数据分布：accurate_result 只有 3 个值（-1/0/1）、sync_status 只有 2 个值，单列区分度都低得可怜——按区分度公式看"好像无法优化"。三层破局：① 区分度是单列的尺子，索引价值看组合命中集——两列各自低基数 ≠ 组合后命中集大；② 业务沟通改变数据分布认知（第 4 步是关键动作）——业务每 5 分钟扫一批、处理完把 sync_status 置 1，任意时刻未处理工作集只有千级，300 多万行是处理完的死数据；业务保证了不平衡 → 小工作集 → 索引稳赚；③ 联合索引让两条件都变定位条件——(accurate_result, sync_status) 上前者等值钉前缀、后者 IN(0,2,4) 是三个等值范围（IN 不算断点，地基⑤ 例外①），两步定位圈出 ~1000 行：扫描量 361 万 → 千级，6.22s → 0.20s（30 倍）。为什么单列索引不够：accurate_result=1 命中 97 万行，单列索引要逐行回表验 sync_status，回表比例太高优化器干脆放弃索引回全表扫（呼应链 2 补充的优化器行为）；联合索引把过滤全压进索引，命中集直接缩到千级。

收拢判据：区分度 0.1 的经验值是单列快速筛查的启发式，不是定律——真正的问题只有一个："这个 WHERE 最终剩多少行"，剩得少就值得索引定位，哪怕每列都是低基数。金句兜底（美团原文结尾）："任何数据库层面的优化都抵不上应用系统的优化"——这个案例的优化信息一半来自数据，一半来自业务。

你的实战锚点：和你的慢 SQL 集中整改互为印证——能说出"我们当时也是先看数据分布、再问业务处理节奏"这种话，面试官就知道你真做过"找业务方沟通"这一步，而不是只会 explain。

★★★ 链 4 · 四个隔离级别？InnoDB 默认哪个？MVCC 怎么实现的？

一层：读未提交 / 读已提交 / 可重复读 / 串行化，分别对应脏读、不可重复读、幻读三个问题。InnoDB 默认 RR（可重复读）。

追问①：MVCC 怎么实现 RR？
每行有两个隐藏列：最近修改它的事务 id（trx_id）和回滚指针（roll_pointer），沿指针在 undo log 里串出版本链。事务第一次快照读时生成 ReadView（当前活跃事务列表 + 高低水位），沿版本链找"对本事务可见"的那个版本。关键差异：RC 每条快照读都新建 ReadView，RR 复用第一次的——这就是"可重复读"三个字的实现。

追问②：RR 到底解没解决幻读？
分两种读答：快照读靠 MVCC 解决；当前读（update / delete / select for update）靠 next-key lock 解决。陷阱题：先快照读、再当前读，仍可能看到别的事务新插入的行——因为当前读读的是最新版本。能主动讲出这个陷阱，RR 这题就封顶了。

追问③：为什么很多大厂规范反而强制 RC + row 格式 binlog？
RC 下基本没有间隙锁 → 并发度更高、死锁概率更低；主从一致性由 row 格式 binlog 兜底。RR 的间隙锁很大程度是 statement 格式 binlog 时代的历史包袱。这一层答出来 = 你理解设计动机，不只是背行为。

★★★ 链 4 补充 · 脏读 / 不可重复读 / 幻读到底差在哪？电商里长什么样？

统一框架：三个都是"同一事务内两次读结果不一致"，按两个维度区分——别人干了什么 × 你读的对象。脏读：读到别人没提交的版本（危害：这版本可能回滚，从未真正存在）；不可重复读：同一行被已提交事务 UPDATE/DELETE，两次读值变了；幻读：同一范围条件被已提交事务 INSERT 新行，两次读行数变了。"未提交"的界定单位是版本（每个版本头上盖着 trx_id 戳），不是"同一行"或"范围"——点查和范围扫都可能脏读。

幻读 ≈ 范围版的不可重复读，SQL 标准里两者定义本来就挨着；分开定义是因为成因不同 → 解法不同：防不可重复读，锁住那一行就够（记录锁）；防幻读，锁行没用——你要防的行"还不存在"，锁不住不存在的东西，只能锁间隙。这就是间隙锁 / next-key lock 存在的根本理由（桥接链 5）。

电商事故形态（被问"实际场景"时讲）：不可重复读 → 库存超卖（check-then-act：select stock=1 → 判断 → update，两个事务都读到 1 都通过）、支付回调 vs 超时取消竞态（按旧状态把已支付订单取消了）；幻读 → 防重插入（select count(*)=0 → insert，RR 快照读互相看不见对方的未提交插入 → 重复扣费 / 重复下单）、秒杀优惠券多发、结算批处理对不上。关键认知：MVCC 保护"读的一致性"，保护不了"先查再写"的业务动作——check 是快照读、act 是写，两个事务各看各的旧世界。

三板斧（对应三类事故的工程解）：① check 变当前读（select ... for update：加锁 + 读最新版本）；② check+act 合并成一条原子 SQL（update ... where stock>0，判断和扣减同一语句完成）；③ 唯一约束兜底——insert 的唯一性检查是当前读语义，直接撞索引最新记录，第二个 insert 报 duplicate key。

金句（加分点）："幻读在生产事故报告里从来不叫幻读——它叫超卖、叫重复扣费、叫对账不平。"案例：火山引擎生鲜秒杀超卖 287 单复盘（根因：回调重试无幂等 + 行锁超时 + Redis/DB 不一致；防护三原则：幂等 / 事务闭环 / 缓存不替库）——链接在资源库 · 事务与 MVCC 阅读包。

你的实战锚点（直接勾连）：充电宝四次扣费就是"防重插入"场景——你们的修复（防重表 + 唯一约束）之所以有效，是因为唯一约束的冲突检查是当前读语义。面试讲这段时把概念收回来："四次扣费本质是 check-then-act 在 RR 快照读下的幻读族问题，唯一约束是兜底锁。"

★★★ 链 4 补充② · 快照读和当前读怎么分？跟隔离级别有没有关系？

判据就一条：读的是"快照"还是"当下最新已提交版本"，要不要加锁。快照读 = 裸 SELECT，不加锁，沿 undo log 版本链读 ReadView 框出的历史版本——读写不互斥，所以并发高；当前读 = SELECT ... FOR UPDATE（X 锁）/ SELECT ... LOCK IN SHARE MODE（S 锁）/ INSERT / UPDATE / DELETE，加锁读最新已提交版本。

两个反直觉点钉死：① UPDATE / DELETE 也是当前读——update stock=stock-1 不是盲目改，是先当前读出该行最新版本（并加锁）再改。所以 RR 的快照保护不到写：事务里裸 SELECT 看到 stock=100 可能是旧快照，UPDATE 时读到的永远是最新值。② 当前读是三板斧的第一板——防超卖的 select ... for update 就是故意放弃快照、强制读最新值并锁行；火山 287 单超卖的病因之一，正是拿普通快照读去做库存校验。

RR 怎么解决不可重复读：ReadView 只建一次，整个事务复用。ReadView 四字段：m_ids（此刻活跃未提交事务列表）、min_trx_id（低水位）、max_trx_id（高水位）、creator_trx_id（自己）。拿版本链上每个版本的 trx_id 对快照判可见性：< 低水位 → 可见（拍快照前已提交）；≥ 高水位 → 不可见（拍快照后才开启）；落在水位之间 → 在 m_ids 里则不可见（仍活跃），不在则可见；自己改的永远可见。不可见就顺 roll_pointer 往 undo log 版本链找下一个旧版本——这就是快照读的实体。RC 和 RR 的唯一差别在拍照时机：RC 每条 SELECT 新建 ReadView（所以能读到别人新提交的）→ 不可重复读；RR 第一次快照读建好、复用到底（快照冻结）→ 可重复读。一句话："可重复读"不是锁出来的，是"一张 ReadView 用到底"钉出来的。

"快照读/当前读不区分隔离级别"——对一半：分法本身不随级别变（RC、RR 下裸 SELECT 都是快照读），变的是行为——隔离级别调两个旋钮：快照读的拍照时机（RC 每语句 / RR 整事务）和当前读的锁范围（RC 基本只行锁 → 当前读防不住幻读 / RR next-key lock → 防得住）。两个例外钉死：读未提交直接读最新版本、连未提交的都读，没有"快照"可言；串行化下裸 SELECT 自动转成 LOCK IN SHARE MODE，快照读整个消失、全变当前读——美团 innodb-lock 原文吐槽的就是这句："不要看到 select 就说不会加锁了，Serializable 这个级别还是会加锁的！"

面试口径（被反问"这两种读和隔离级别什么关系"时不卡壳版）："快照读和当前读是读法分类，本身不随隔离级别变；隔离级别调的是它们的行为——快照读的 ReadView 创建时机（RC 每语句、RR 整事务）和当前读的锁范围（RC 行锁、RR next-key lock）。Serializable 下快照读退化成当前读。"

★★★ 链 4 补充③ · MVCC 凭什么做"并发控制"？trx_id 和 ReadView 怎么配合？

并发冲突只有三类，每类用最便宜的机制处理：读↔读无冲突，不用管；读↔写（脏读 / 不可重复读 / 幻读全属此类）由 MVCC 无锁化——写不阻塞读、读不阻塞写；写↔写（丢失更新）MVCC 管不了，必须行锁互斥。所以 InnoDB 并发控制是两条腿：MVCC 把最高频的读写冲突无锁化，锁只留给写写。MVCC = 多版本存储（undo 版本链 + 隐藏列 trx_id）× 可见性仲裁（ReadView）——没有版本链，ReadView 判了也没旧版本可读；没有 ReadView，版本链躺着不知道给谁看。

trx_id 生命周期（反直觉：begin 时不分配）：全局单调递增计数器，第一次写操作才分配（insert / update / delete；select for update 这类加锁当前读也要分配——锁得挂在有身份的事务上）；只读事务全程没有 trx_id，ReadView 的 creator_trx_id 记 0。懒分配的动机：只读事务占大多数，省一次全局计数器争抢；单调递增的动机：id 大小就是时间先后，可见性判断全靠这个序。commit 后退出活跃名单，但 id 永远留在行版本上，直到 purge 线程确认没有任何活跃 ReadView 需要旧版本才物理清理。

版本链上的 trx_id 钉死不变：每个版本永远盖"创造它的事务"的 id，旧版本进 undo 链时带着当年的老戳，后来者改这行不会给它换戳。观察到的"trx_id 会变"，真相是每次 UPDATE 往链头压一个盖新戳的版本——"当前版本"这个位置换人，不是旧版本改戳。DELETE 也算一次修改（打删除标记、换新戳），物理删除留给 purge。

可见性判断 = 把 trx_id 轴切成三段：

      段① 已提交区        段② 待定区          段③ 未出生区
  ─────────────┼──────────────────┼──────────────▶ trx_id
           min_trx_id          max_trx_id
          (m_ids 最小值)     (下一个待分配 id)
      必然可见         在 m_ids → 不可见       必然不可见
                       不在 → 可见（已提交）
  段①: trx_id < min ｜ 段②: [min, max) 左闭右开 ｜ 段③: trx_id >= max

段①为什么必然可见：min 是"此刻还在跑的最老事务"，比它小的若还没提交，那它自己就该是 min——矛盾。段③为什么必然不可见：id ≥ max 意味着拍照时这个号还没发出去，事务此刻不存在。段②为什么必须查名单：号已发出，状态只有两种——还在跑（在名单）/ 已提交（不在名单），名单就是完备判据，不能只用大小一刀切。开闭区间防晃点：两个端点殊途同归都不可见，但原因不同——trx_id == min 落在段②（它就是活跃名单里最小的那个，查名单必然命中）；trx_id == max 落在段③（这个号拍照时还没发出去）。再钉一个考点：trx_id == max-1（拍照前发出的最后一个号）落在段②，必须查名单。特例：等于 creator_trx_id（自己改的）永远最先判、可见。能反杀追问的例子：版本戳比 creator 大、落在待定区，仍可能可见——只要它拍照前已提交（领号早、提交得也快）。

四事务时序推演（盯三件事：trx_id 分配时机 / ReadView 创建时机 / 链头增长）：

t0  初始: 当前(100,trx=80) → (50,trx=60)；全局计数器=102
t1  A: begin; UPDATE stock=99 → A 分配 trx_id=102，计数器→103
    链: (99,102)→(100,80)→(50,60)，A 未提交
t2  B: begin; UPDATE id=2 → B 分配 trx_id=103，计数器→104
t3  C: begin; SELECT id=1（只读，无 trx_id）
    → 创建 ReadView: creator=0, m_ids=[102,103], min=102, max=104
    → (99,102) 在 m_ids → 不可见 → (100,80) 可见，读到 100
t4  A: COMMIT（退出活跃名单）
t5  C: SELECT id=1
    RR: 复用 t3 的 ReadView → 102 仍在 m_ids → 还是 100
    （RC: 重建 → m_ids=[103] → 102 不在 → 读到 99）
t6  B: UPDATE id=1（当前读拿到 99，改 98）; COMMIT
    链: (98,103)→(99,102)→(100,80)→(50,60)
t7  C: SELECT id=1 → 仍用 t3 的 ReadView
    (98,103) 在 m_ids ✗ → (99,102) 在 m_ids ✗ → (100,80) 可见
    读到 100（连走两级版本链）
t8  D: begin; UPDATE id=3 → 分配 104；SELECT id=1
    → 新 ReadView: m_ids=[104], min=104, max=105
    → (98,103): 103 < min → 可见，读到 98

30 秒口径："MVCC 管读写冲突、锁管写写冲突。trx_id 第一次写才从全局递增计数器分配，跟着自己产出的版本走、钉死不变；ReadView 用 min / max / m_ids 把 id 轴切成三段，可见性就是拿版本的戳对这三段。RC 每条语句新建 ReadView，RR 一张用到提交——两级全部差异就这一个开关。"

★★☆ 链 4 补充④ · MVCC 和 Java 并发有什么异曲同工？（封顶追问弹药）

同一套思想在两个领域的落地：并发控制的第一性问题相同——冲突分类，每类用最便宜的机制处理。

MySQL（InnoDB）Java
读写冲突MVCC 无锁化：读旧版本，不加锁CopyOnWriteArrayList：读旧快照，不加锁
写写冲突行锁互斥，悲观排队COW 写时 ReentrantLock / synchronized / CAS
可见性规则ReadView + trx_id 版本戳happens-before / volatile / 内存屏障

最精确的对应物是 CopyOnWriteArrayList：它的 iterator 一旦创建，看到的就是创建那一刻的数组，之后别人怎么改都看不到——这就是 RR 复用 ReadView；每次 get 直接读当前数组、每次看最新——对照 RC 每条语句重建。读全程不加锁、读写互不阻塞，和 MVCC 一模一样；写要加锁，对应 MVCC 管不了的写写冲突。

三个差别（加分项在这）：① 冗余方式：COW 每次写全量拷贝整个数组，InnoDB 只为改过的行存增量旧版本（undo 链）——所以 COW 只敢用在读极多写极少处，MVCC 敢扛高并发写；② 写写冲突：Java 有 CAS 乐观重试，InnoDB 一律悲观行锁排队——数据库丢不起 lost update；③ 垃圾清理：COW 靠 GC，MVCC 靠 purge 线程清理没有 ReadView 需要的旧版本——所以长事务是 MySQL 大忌：purge 不敢删，undo 表空间越胀越大。

封顶口径："MVCC 在 Java 里的孪生兄弟是 CopyOnWriteArrayList——读快照、写加锁、读写不互斥。区别是 InnoDB 用 undo 链存增量版本而非全量拷贝，写写冲突也没有乐观重试、只能行锁互斥。本质同一个设计：按冲突类型选机制，读写冲突用版本冗余换无锁，写写冲突才付锁的代价。"——这句出口，Java 和 MySQL 两头的追问都接得住。

★★★ 链 5 · InnoDB 的行锁有哪几种？死锁怎么排查？

一层：记录锁（锁单行）、间隙锁（锁开区间，防插入）、next-key lock（记录 + 间隙，左开右闭，RR 的默认加锁单位）、插入意向锁；表级还有意向锁（IS/IX）和 MDL 元数据锁。最核心一句：行锁锁的是索引记录，不是物理行——没走索引就没有行锁可言。

追问①：update 没走索引会发生什么？
无法用索引定位行 → 全表扫描 → 扫到的每一行都加 next-key lock，间隙全锁 → 效果等于锁全表。生产上"一个 update 拖垮整张表"的经典事故就是这么来的。

追问②：死锁怎么排查？
show engine innodb status 看 LATEST DETECTED DEADLOCK：两个事务各持有什么锁、在等什么锁，画成环就是死锁。高频成因：加锁顺序不一致（A 锁 1→2，B 锁 2→1）；唯一索引并发 insert 冲突；间隙锁范围重叠。预防四招：固定加锁顺序、缩短事务、降级隔离级别、热点行拆分。

追问③（唯一索引专项）：唯一索引和普通索引加锁有什么区别？
等值查询命中唯一索引时，next-key lock 退化为记录锁（不用防"相同的值再插一个"）；普通索引不退化，间隙照锁。所以唯一索引并发更高——这也是"能用唯一索引就别用普通索引"的底层原因。

你的实战锚点（双份）：① 你排查过锁表死锁——今晚花 30 秒回忆：哪张表、什么业务并发、怎么定位、最后怎么改的；② 四次扣费的修复用了防重表 + 唯一约束，被问唯一索引时主动勾连："我们做支付幂等就是靠唯一索引兜底的。"

★★☆ 链 6 · 一条 update 在 InnoDB 里完整走一遍？表太大了怎么办？

一层：加载数据页进 buffer pool → 写 undo log（回滚 + MVCC 版本链）→ 改内存页 → 写 redo log（prepare 状态）→ 写 binlog → redo log 置 commit。三大日志分工：undo 保原子性和 MVCC，redo 保持久性（WAL：先写日志再写盘），binlog 管主从复制和数据恢复。

追问①：redo 为什么要两阶段提交？
为了让 redo 和 binlog 逻辑一致。崩溃恢复时：redo 已 prepare 且 binlog 完整 → 提交；否则回滚。没有两阶段，就可能主库提交了但从库没收到 binlog——主从不一致。

追问②：表多大该分库分表？
先给标尺（阿里规约：单表 500 万行或 2GB 考虑分表，实际看查询响应），再给"不分的替代方案"——这才是分层答案：索引优化 → 读写分离 → 冷热分离 / 历史归档 → 缓存。真要分：先垂直（按业务域拆）后水平（按分片键拆），分片键选最高频的查询维度。分完的新问题三连：全局 ID、跨分片查询、分布式事务——这三个词一出口，面试官就知道你真想过。

你的实战锚点（必带）：话费项目月百万级数据归档方案——"我们没有一上来就分表，先做的历史归档 + 冷热分离，用最低成本解决了查询变慢。"这就是追问②里"替代方案"那层的活证据。

第三部分 · 地基链 1 地基：SQL 是怎么被执行的（《MySQL 实战 45 讲》第 1 / 2 / 4 讲）

六条链的答案为什么长这样？因为 MySQL 就是这么跑的。这一节是链 1 / 3 / 4 / 6 共同的地基——看懂执行流程，后面每条链的"为什么"会自己长出来。对照《MySQL 实战 45 讲》（林晓斌）第 1、2、4 讲。

① 一条查询语句的执行：先记住两层架构

MySQL 分 Server 层（连接器、查询缓存、分析器、优化器、执行器——跨引擎功能全在这层）和存储引擎层（插件式，5.5.5 起默认 InnoDB）。不同引擎共用一个 Server 层——这是理解"为什么有两份日志"的钥匙。

① 连接器建连、认证、缓存权限（改权限对已有连接不生效）。长连接吃内存：临时内存绑在连接上，断开才释放 → 5.7+ 用 mysql_reset_connection。空闲超 wait_timeout（默认 8h）被断。
② 查询缓存（8.0 已整块删除）key = SQL 原文，value = 结果。一个更新让整张表缓存全失效——命中率太低，所以 8.0 删了。面试问"为什么删"就答这句。
③ 分析器词法分析（认出 select / T / ID 各是什么）→ 语法分析（合不合法）→ 语义分析（列和表存不存在——Unknown column 'k' 报在这步）。
④ 优化器多索引选哪个、多表 join 定连接顺序。逻辑等价的方案效率天差地别，优化器负责挑。
⑤ 执行器先校验表级权限 → 调引擎接口逐行取数（无索引全表扫；有索引调"取第一行 / 下一行"接口）。慢日志的 rows_examined 在这里累加——链 3 的 explain 从这接。
30 秒面试版（背骨架，出声练） "MySQL 分 Server 层和引擎层。查询过五个组件：连接器管认证和权限缓存；8.0 之前有查询缓存，因为任何更新都让整表缓存失效，被整块删了；分析器做词法、语法、语义分析；优化器选索引、定 join 顺序；执行器校验表权限后调引擎接口逐行取数。"

② 一条更新语句的执行：多出两份日志 + 两阶段提交

前半程与查询相同，区别在引擎层。以 update T set c=c+1 where ID=2 为例，执行器与 InnoDB 配合五步：

1 · 取行数据页不在内存，先从磁盘读入 buffer pool。
2 · 改内存执行器算出新值，调引擎接口写入。
3 · 写 redo log（prepare）引擎先记日志——WAL：先写日志再写磁盘，此刻更新即算完成。
4 · 写 binlog执行器生成 binlog 并落盘。
5 · 提交（redo 置 commit）prepare → binlog → commit，这三步就是两阶段提交。

WAL 的类比（45 讲原文）：redo log 是掌柜手边的粉板（赊账先记粉板，快），磁盘数据页是账本（空闲时再誊）。异常重启按粉板恢复 = crash-safe。redo log 固定大小循环写：write pos 写位置、checkpoint 擦除位置，写满必须停下推进 checkpoint——这就是 redo log 不能无限大的原因。

为什么有两份？历史原因：早期 MyISAM 没有 crash-safe 能力，binlog 只能归档；InnoDB 以插件形式进来时自带 redo log，两套并存至今。

两阶段提交为什么必须？反证法（设 c 从 0 改 1，写完第一个日志就崩溃）：先 redo 后 binlog → 主库恢复 c=1，但 binlog 没这条，用"全量备份 + binlog 重放"搭出的从库 c=0；先 binlog 后 redo → 主库回滚 c=0，但从库重放后 c=1。两种都主从不一致。所以崩溃恢复的判定是：redo 为 prepare 且对应 binlog 完整 → 提交，否则回滚。配套"双 1"参数：innodb_flush_log_at_trx_commit=1、sync_binlog=1。

30 秒面试版（背骨架，出声练） "更新前半程同查询。到引擎层：取行、改内存、写 redo log 置 prepare；执行器写 binlog；提交时 redo 置 commit——这就是两阶段提交。redo 是引擎层物理日志、循环写，保 crash-safe；binlog 是 Server 层逻辑日志、追加写，保主从复制和归档。两阶段提交保证崩溃恢复时两份日志逻辑一致，否则主从会岔。"
undo log 在哪？ 第 2 讲没展开（45 讲放在事务章）。按链 6 的分工记：undo 保原子性 + MVCC 版本链，redo 保持久性，binlog 管复制和恢复。

③ B+ 树 / 哈希 / 红黑树 / B 树大比对：先讲推理链，再上结论

45 讲第 4 讲的精华不是结论，是推理路径——面试照这个讲，比背结论高一档：

  1. 数据库索引的目标函数不是"比较次数少"，是"磁盘 IO 次数少"（机械盘一次随机读约 10ms，IO 次数就是命）。
  2. 树高 ≈ IO 次数 → 树必须矮 → 必须 N 叉，不能二叉（100 万节点的二叉树高 20 = 20 次随机 IO，不可接受）。N 就是扇出——一个节点能装多少个"指向下一层的指针"，由页大小决定：InnoDB 一页 16K，每条"键 + 指针"约 14 字节 → N ≈ 1200。容量 = 扇出树高-1 × 每叶子页行数：扇出是指数底数，所以"键越小 → 扇出越大 → 树越矮"——自增 bigint 8 字节对 UUID 36 字节，扇出约 1170 对 390，这是强制自增主键的另一半理由。
  3. N 叉树的两个变体：B 树每个节点都存数据 → 扇出小 → 树更高；B+ 树非叶子只存键 → 扇出拉满 → 更矮，且叶子间链表让范围查询顺着走。
  4. 所以结论不是"B+ 树最好"，而是"按访问模式选结构"——这才是架构师口径。

④ h = logm+1(N)：美团那篇的树高公式，逐符号拆开

读美团《MySQL 索引原理及慢查询优化》会在"b+ 树性质"第 1 条撞上这个公式：h = logm+1(N)。原文给了三个符号：N = 数据表总记录数；m = 每个磁盘块（一个数据页）里数据项（索引键）的个数；h = 树高 ≈ 查一条记录的磁盘 IO 次数。

谁是底、谁是真数：(m+1) 是底数（下标），N 是真数——读作"以 m+1 为底 N 的对数"，等价于 (m+1)h = N。也就是说，h 回答的问题是"(m+1) 连乘几次才能盖住 N 条记录"。

为什么底数是 m+1 而不是 m：m 个键把值域切成 m+1 段，所以一个节点有 m+1 个指针——扇出就是 m+1（美团那张图里磁盘块 1 有 17、35 两个数据项，对应 P1 / P2 / P3 三个指针）。满员的树每往下一层覆盖量 ×(m+1)：第 1 层 1 个块、第 2 层 m+1 个、第 3 层 (m+1)²……总容量 ≈ (m+1)h，两边取对数反解出 h。注意符号撞车：上面 ③ 和 45 讲口径里用 N 指扇出（≈1200），美团公式里 N 是总记录数、扇出写作 m+1——两个 N 不是一回事，坐在底数位置上的那个才是扇出。

为什么 N 一定时 m 越大 h"反而"越小："反而"的别扭感来自把 m 当成了真数——log 对真数是增函数，对底数是减函数，而 m 坐在底数位置上。换底公式一眼看穿：h = ln N ÷ ln(m+1)，N 固定分子就固定，m 越大分母越大、h 越小。直觉版：每层把搜索范围缩小 (m+1) 倍，倍率越大需要的层数越少——树越"矮胖"。

⑤ 最左前缀的底层原理：联合索引是一条"字典序"元组列表

链 1 追问③ 的口诀"范围之后全断"凭什么成立？把联合索引 (a,b,c,d) 的物理形态建立起来，所有现象自己长出来：叶子层是一条按"元组字典序"排好的线性列表——先按 a 排，a 相等按 b 排，b 相等按 c 排，依此类推；B+ 树只是这条列表上方的二分定位器（非叶子层的分隔键也是元组，比较时先比 a、相等再比 b）。全部推论都从一条性质长出来：后一列的有序是局部的——只在前一列取值相等的分组内部成立，全局看是乱的。这就是电话簿：按（姓，名）排序，"名"只在同姓内部有序，所以"查所有姓张的"很快，"查所有名叫伟的"得翻整本。

⑥ Buffer Pool 与三大日志的因果链：为什么 undo 保原子性、redo 保持久性

Buffer pool 三问（地基①② 的补丁）：是什么——InnoDB 在内存里开的一大块缓存，缓存单位是 16KB 页（数据页 / 索引页 / undo 页的内存副本），读先查它、写先改它（改过的叫脏页，后台线程慢慢刷盘）；在哪——内存，mysqld 启动时向 OS 申请，innodb_buffer_pool_size 控制（默认 128MB，生产一般给物理内存 50%-70%）；属于谁——InnoDB 引擎层，不是 Server 层（8.0 删了查询缓存后 Server 层彻底不碰数据缓存；MyISAM 只有缓存索引块的 key_buffer）。判别口诀：跨引擎通用的功能在 Server 层（binlog），引擎特有的在引擎层（buffer pool、redo）。

层有什么记什么
Server 层（跨引擎通用）连接器 / 分析器 / 优化器 / 执行器、binlog不缓存任何数据
InnoDB · 内存Buffer Pool（16KB 页缓存 + Change Buffer + 自适应哈希 AHI）、Redo Log Bufferbuffer pool 是引擎层私有财产
InnoDB · 磁盘.ibd（表数据 + 索引，B+ 树本体）、undo log 文件、redo log 文件16KB 页是磁盘 ↔ 内存之间的"货币单位"

因果链（一条链串起三大日志）：① 为了快，读写都先打 buffer pool，不直接碰磁盘 → ② 提交 ≠ 落盘（提交时只刷 redo 那几百字节顺序写，脏页以后慢慢刷）→ 崩了数据页是旧的 → redo 负责"重做"，保持久性；③ 反过来脏页刷盘不看事务脸色（没提交的半成品可能已在盘上）→ 崩了要把半成品擦掉 → undo 负责"撤销"，保原子性。一句话：buffer pool 是性能的答案，undo 和 redo 是这个答案的两份代价的解法。

字面助记（纠偏版）：日志名 = 崩溃恢复时对它执行的动作。undo log 用来做撤销 → 装的是修改前的旧值（不是"修改后的记录"！）；redo log 用来做重做 → 装的是修改后的新值（物理日志：哪个页哪个偏移改成什么）。redo 的职责边界很窄——只保已提交事务不丢；"全成功或全失败"是原子性，归 undo 管。

崩溃恢复的真实两步（被深挖时讲这个） ① redo 回放：把 redo log 里所有修改全部重做进数据页——包括没提交事务的半成品，也一并重做（回放不区分提交与否）；② undo 回滚：找出崩溃时未提交的事务，用 undo log 逐个擦掉。防追问：undo 页本身也是数据页，它的修改同样先记 redo——undo log 的持久化也是 redo 保证的（WAL 覆盖所有页修改）。

两个"为什么"防追问：① 为什么不用 OS 文件缓存、非要自建 buffer pool？进程内缓存可以定制策略（LRU、加锁、change buffer），OS 缓存做不到——所以 InnoDB 用直接 I/O 绕过 OS 缓存，避免双份缓存；② buffer pool 的 LRU 不是纯 LRU：新页插在 5/8 处（midpoint），全表扫描冲进来的页进不了热区头部——防的就是一次大扫描把热点页全挤出去。
