第二部分 · 正课六条追问链

点击展开。先看题 → 盖住 → 出声讲 → 再对答案。黄色"你的实战锚点"是讲完标准答案后主动带出来的加分动作。

★★★ 链 1 · MySQL 索引为什么用 B+ 树，不用哈希 / 红黑树 / B 树？

一层：哈希索引只支持等值查询，范围、排序、模糊全废；红黑树是二叉树，数据量大了树太高，每层一次磁盘 IO 扛不住；B 树非叶子节点也存数据，单页能放的索引项少；B+ 树非叶子只存"键 + 页指针"，单页扇出大 → 树矮胖（千万级只要 3 层），且叶子节点是双向链表，天然支持范围查询和排序。

追问①：3 层 B+ 树到底能存多少行？算给我看。
页大小 16K；非叶子页一个"键 + 指针"约 14 字节（bigint 8B + 指针 6B），单页扇出约 1170；叶子页按每行 1K 算存 16 行 → 1170 × 1170 × 16 ≈ 两千两百万行。且根节点常驻内存，实际磁盘 IO 只有 1-2 次。——能算出这个数字的人，全场面试不超过三个。

追问②：为什么所有规范都强制自增主键？用 UUID 会怎样？
一句话：聚簇索引的数据按主键顺序存放，插入位置由主键决定。自增 = 永远追加到最右页：写满就申请新页、旧页不动、写盘是顺序写。UUID = 插进中间的随机页，引发三步灾难：① 页分裂——目标页满了要劈：申请新页、搬走一半行、改链表、父页加指针（父页满了级联再劈）；② 页碎片——一个满页变两个半满页，长期下来叶子页平均只装五六成满：表膨胀、范围扫描读更多页、buffer pool 一半装空气；③ 随机 IO——目标页随机 → 大概率不在 buffer pool，先随机读进内存再随机写回；磁盘层面从文件末尾追加写变成散布全文件的随机写。外加扇出那一刀：UUID 36 字节 → 扇出从 ~1170 掉到 ~390（见地基节），树更高；且二级索引叶子存主键值，每一棵二级索引都跟着变大。再追一层（防身）：非唯一二级索引的随机写入，InnoDB 有 change buffer 缓解——修改先缓存，页被读进内存时再合并（45 讲第 9 讲）。

追问③：联合索引 (a,b,c)，where b=? 走不走索引？where a=? and b>? and c=? 呢？
前者不走——索引内部是先按 a 排、a 相同再按 b 排，没有 a，b 在整棵树里无序，只能全扫（MySQL 5.6+ 可能走 ICP 索引下推做引擎层过滤，但那不是"用索引定位"）。后者：c 用不上——b 是范围条件，b 之后 c 无序。口诀：范围之后全断。

★★★ 链 1 补充 · MySQL 有哪些类型的索引？（先分维度再枚举）

答法骨架："分三个维度——按物理存储、按逻辑用途、按数据结构。"先给骨架再展开，结构化本身就是分。

① 按物理存储（InnoDB 最核心）：聚簇索引叶子存整行，一张表只有一棵（数据只能按一种顺序物理存放），就是主键那棵 B+ 树——字典的正文，目录和内容长在一起；二级索引叶子存"索引列 + 主键值"，可以很多棵，查整行要回表——部首检字表查到的只是页码，还得翻回正文。没主键时 InnoDB 选第一个非空唯一索引顶上，都没有就生成 6 字节隐藏 row_id——这就是"表必须有主键"的底层原因。对照组：MyISAM 没有聚簇索引，叶子存数据行的磁盘地址，次次回表——聚簇 = 数据跟着索引走。

② 按逻辑用途：主键 / 唯一（允许 NULL；接链 5：等值命中时 next-key 退化为记录锁，并发更高）/ 普通 / 联合（最左前缀说的就是它）/ 前缀（长字符串只索引前 N 字符，省空间但不能用于排序）。注意：覆盖索引不是类型，是用法——查询列全在索引里就免回表（接链 2）。

③ 按数据结构：B+ 树默认全能（本课全部地基）；哈希——Memory 引擎默认，等值 O(1) 范围全废，InnoDB 还有个不可控的自适应哈希索引 AHI（热点页自动建哈希，提一嘴是加分）；全文 FULLTEXT——倒排思路（词 → 文档列表），5.6 起 InnoDB 支持，5.7.6 内置 ngram 才真正支持中文；空间 R-Tree——地理位置 GIS，5.7 起。

④ 版本线（证明你用的是 2026 年的 MySQL）：5.6 → ICP 索引下推（链 1 追问③那个）；5.7 → 生成列（给生成列建索引 = 变相函数索引）；8.0 → 真正的降序索引（5.7 写了语法会被悄悄忽略）、不可见索引（想删索引又怕出事？先设 invisible 观察一阵 = 影子删除）、函数索引（8.0.13，"列上套函数索引失效"这条有了官方解法）、多值索引（8.0.17，给 JSON 数组建）。

你的实战锚点：慢 SQL 整改经历 + "下线索引前先设 invisible 观察"——把 8.0 新特性和你的真实治理动作绑在一起讲，非常像干过活的。

★★★ 链 2 · 什么是回表？怎么避免？

一层：二级索引的叶子节点只存"索引列 + 主键值"。查到之后还要拿主键去聚簇索引把整行捞出来——这一趟额外的查找叫回表。

追问①：什么是覆盖索引？
查询要的所有列都在索引里，不用回表，explain 的 Extra 显示 Using index。实战动作：高频查询把返回列设计进联合索引。但补一句权衡：索引越宽，写入维护成本和回表收益要一起算——这句话出口，面试官知道你不是背书的。

追问②：select count(*) 走什么索引？InnoDB 为什么不缓存总行数？
优化器会选最小的那棵二级索引扫（页数少、更便宜）。不缓存行数是因为 MVCC——同一时刻不同事务"可见的行数"不一样，缓存没有定义。对比：MyISAM 没事务，所以可以缓存。

你的实战锚点：话费充值平台 TPS 500 的订单查询——哪些查询走覆盖索引、哪些必须回表，讲链 3 整改故事时顺手带上。

★★★ 链 3 · 线上接口慢了，怀疑是 SQL，你的排查路径？

一层：四步走：① 慢查询日志（long_query_time）+ 监控定位到具体 SQL；② explain 看执行计划——type 至少到 range（ALL = 全表扫描，立刻报警）、key 是实际走的索引、rows 是扫描行数、Extra 警惕 Using filesort / Using temporary；③ 对症下药：缺索引补索引、改写 SQL（拆复杂 JOIN / 覆盖索引 / 延迟关联）、热点上缓存；④ 验证：对比优化前后 rows 和耗时，灰度观察。"定位 → 量化 → 对症 → 验证"这八个字是骨架，先说骨架再展开。

追问①：深分页 limit 1000000, 10 为什么慢？怎么优化？
要扫出前 100 万 + 10 行再丢掉前 100 万。两种改法：游标式 where id > 上页最大id limit 10（聚簇索引范围扫，最快）；或延迟关联——先用覆盖索引只查出 10 个 id，再回表取整行。

追问②：明明有索引，explain 却没走，有哪些可能？
失效清单一口气背：列上做函数或运算；隐式类型转换（varchar 列传了数字）；like 前导 %；OR 两边不都有索引；不满足最左前缀；优化器估算全表反而更快（表太小 / 回表比例太高）。最后一项的解法：analyze table 更新统计信息，或 force index 强制验证。

你的实战锚点（王牌，讲完链路主动带）："我在嘉立创做过一轮慢 SQL 集中整改——复杂 SQL 拆分 + 索引调整 + 热点上缓存。"今晚把这个故事的三件事各回忆一个具体例子：哪张表、什么现象、改完快了多少。

★★★ 链 4 · 四个隔离级别？InnoDB 默认哪个？MVCC 怎么实现的？

一层：读未提交 / 读已提交 / 可重复读 / 串行化，分别对应脏读、不可重复读、幻读三个问题。InnoDB 默认 RR（可重复读）。

追问①：MVCC 怎么实现 RR？
每行有两个隐藏列：最近修改它的事务 id（trx_id）和回滚指针（roll_pointer），沿指针在 undo log 里串出版本链。事务第一次快照读时生成 ReadView（当前活跃事务列表 + 高低水位），沿版本链找"对本事务可见"的那个版本。关键差异：RC 每条快照读都新建 ReadView，RR 复用第一次的——这就是"可重复读"三个字的实现。

追问②：RR 到底解没解决幻读？
分两种读答：快照读靠 MVCC 解决；当前读（update / delete / select for update）靠 next-key lock 解决。陷阱题：先快照读、再当前读，仍可能看到别的事务新插入的行——因为当前读读的是最新版本。能主动讲出这个陷阱，RR 这题就封顶了。

追问③：为什么很多大厂规范反而强制 RC + row 格式 binlog？
RC 下基本没有间隙锁 → 并发度更高、死锁概率更低；主从一致性由 row 格式 binlog 兜底。RR 的间隙锁很大程度是 statement 格式 binlog 时代的历史包袱。这一层答出来 = 你理解设计动机，不只是背行为。

★★★ 链 5 · InnoDB 的行锁有哪几种？死锁怎么排查？

一层：记录锁（锁单行）、间隙锁（锁开区间，防插入）、next-key lock（记录 + 间隙，左开右闭，RR 的默认加锁单位）、插入意向锁；表级还有意向锁（IS/IX）和 MDL 元数据锁。最核心一句：行锁锁的是索引记录，不是物理行——没走索引就没有行锁可言。

追问①：update 没走索引会发生什么？
无法用索引定位行 → 全表扫描 → 扫到的每一行都加 next-key lock，间隙全锁 → 效果等于锁全表。生产上"一个 update 拖垮整张表"的经典事故就是这么来的。

追问②：死锁怎么排查？
show engine innodb status 看 LATEST DETECTED DEADLOCK：两个事务各持有什么锁、在等什么锁，画成环就是死锁。高频成因：加锁顺序不一致（A 锁 1→2，B 锁 2→1）；唯一索引并发 insert 冲突；间隙锁范围重叠。预防四招：固定加锁顺序、缩短事务、降级隔离级别、热点行拆分。

追问③（唯一索引专项）：唯一索引和普通索引加锁有什么区别？
等值查询命中唯一索引时，next-key lock 退化为记录锁（不用防"相同的值再插一个"）；普通索引不退化，间隙照锁。所以唯一索引并发更高——这也是"能用唯一索引就别用普通索引"的底层原因。

你的实战锚点（双份）：① 你排查过锁表死锁——今晚花 30 秒回忆：哪张表、什么业务并发、怎么定位、最后怎么改的；② 四次扣费的修复用了防重表 + 唯一约束，被问唯一索引时主动勾连："我们做支付幂等就是靠唯一索引兜底的。"

★★☆ 链 6 · 一条 update 在 InnoDB 里完整走一遍？表太大了怎么办？

一层：加载数据页进 buffer pool → 写 undo log（回滚 + MVCC 版本链）→ 改内存页 → 写 redo log（prepare 状态）→ 写 binlog → redo log 置 commit。三大日志分工：undo 保原子性和 MVCC，redo 保持久性（WAL：先写日志再写盘），binlog 管主从复制和数据恢复。

追问①：redo 为什么要两阶段提交？
为了让 redo 和 binlog 逻辑一致。崩溃恢复时：redo 已 prepare 且 binlog 完整 → 提交；否则回滚。没有两阶段，就可能主库提交了但从库没收到 binlog——主从不一致。

追问②：表多大该分库分表？
先给标尺（阿里规约：单表 500 万行或 2GB 考虑分表，实际看查询响应），再给"不分的替代方案"——这才是分层答案：索引优化 → 读写分离 → 冷热分离 / 历史归档 → 缓存。真要分：先垂直（按业务域拆）后水平（按分片键拆），分片键选最高频的查询维度。分完的新问题三连：全局 ID、跨分片查询、分布式事务——这三个词一出口，面试官就知道你真想过。

你的实战锚点（必带）：话费项目月百万级数据归档方案——"我们没有一上来就分表，先做的历史归档 + 冷热分离，用最低成本解决了查询变慢。"这就是追问②里"替代方案"那层的活证据。

第三部分 · 地基链 1 地基：SQL 是怎么被执行的（《MySQL 实战 45 讲》第 1 / 2 / 4 讲）

六条链的答案为什么长这样？因为 MySQL 就是这么跑的。这一节是链 1 / 3 / 4 / 6 共同的地基——看懂执行流程，后面每条链的"为什么"会自己长出来。对照《MySQL 实战 45 讲》（林晓斌）第 1、2、4 讲。

① 一条查询语句的执行：先记住两层架构

MySQL 分 Server 层（连接器、查询缓存、分析器、优化器、执行器——跨引擎功能全在这层）和存储引擎层（插件式，5.5.5 起默认 InnoDB）。不同引擎共用一个 Server 层——这是理解"为什么有两份日志"的钥匙。

① 连接器建连、认证、缓存权限（改权限对已有连接不生效）。长连接吃内存：临时内存绑在连接上，断开才释放 → 5.7+ 用 mysql_reset_connection。空闲超 wait_timeout（默认 8h）被断。
② 查询缓存（8.0 已整块删除）key = SQL 原文，value = 结果。一个更新让整张表缓存全失效——命中率太低，所以 8.0 删了。面试问"为什么删"就答这句。
③ 分析器词法分析（认出 select / T / ID 各是什么）→ 语法分析（合不合法）→ 语义分析（列和表存不存在——Unknown column 'k' 报在这步）。
④ 优化器多索引选哪个、多表 join 定连接顺序。逻辑等价的方案效率天差地别，优化器负责挑。
⑤ 执行器先校验表级权限 → 调引擎接口逐行取数（无索引全表扫；有索引调"取第一行 / 下一行"接口）。慢日志的 rows_examined 在这里累加——链 3 的 explain 从这接。
30 秒面试版（背骨架，出声练） "MySQL 分 Server 层和引擎层。查询过五个组件：连接器管认证和权限缓存；8.0 之前有查询缓存，因为任何更新都让整表缓存失效，被整块删了；分析器做词法、语法、语义分析；优化器选索引、定 join 顺序；执行器校验表权限后调引擎接口逐行取数。"

② 一条更新语句的执行：多出两份日志 + 两阶段提交

前半程与查询相同，区别在引擎层。以 update T set c=c+1 where ID=2 为例，执行器与 InnoDB 配合五步：

1 · 取行数据页不在内存，先从磁盘读入 buffer pool。
2 · 改内存执行器算出新值，调引擎接口写入。
3 · 写 redo log（prepare）引擎先记日志——WAL：先写日志再写磁盘，此刻更新即算完成。
4 · 写 binlog执行器生成 binlog 并落盘。
5 · 提交（redo 置 commit）prepare → binlog → commit，这三步就是两阶段提交。

WAL 的类比（45 讲原文）：redo log 是掌柜手边的粉板（赊账先记粉板，快），磁盘数据页是账本（空闲时再誊）。异常重启按粉板恢复 = crash-safe。redo log 固定大小循环写：write pos 写位置、checkpoint 擦除位置，写满必须停下推进 checkpoint——这就是 redo log 不能无限大的原因。

维度redo logbinlog
层级InnoDB 引擎特有Server 层，所有引擎通用
内容物理日志："哪个数据页做了什么修改"逻辑日志：原始语句 / 行变更
写法固定大小、循环写（会用完）追加写，写满换文件，不覆盖

为什么有两份？历史原因：早期 MyISAM 没有 crash-safe 能力，binlog 只能归档；InnoDB 以插件形式进来时自带 redo log，两套并存至今。

两阶段提交为什么必须？反证法（设 c 从 0 改 1，写完第一个日志就崩溃）：先 redo 后 binlog → 主库恢复 c=1，但 binlog 没这条，用"全量备份 + binlog 重放"搭出的从库 c=0；先 binlog 后 redo → 主库回滚 c=0，但从库重放后 c=1。两种都主从不一致。所以崩溃恢复的判定是：redo 为 prepare 且对应 binlog 完整 → 提交，否则回滚。配套"双 1"参数：innodb_flush_log_at_trx_commit=1、sync_binlog=1。

30 秒面试版（背骨架，出声练） "更新前半程同查询。到引擎层：取行、改内存、写 redo log 置 prepare；执行器写 binlog；提交时 redo 置 commit——这就是两阶段提交。redo 是引擎层物理日志、循环写，保 crash-safe；binlog 是 Server 层逻辑日志、追加写，保主从复制和归档。两阶段提交保证崩溃恢复时两份日志逻辑一致，否则主从会岔。"
undo log 在哪？ 第 2 讲没展开（45 讲放在事务章）。按链 6 的分工记：undo 保原子性 + MVCC 版本链，redo 保持久性，binlog 管复制和恢复。

③ B+ 树 / 哈希 / 红黑树 / B 树大比对：先讲推理链，再上结论

45 讲第 4 讲的精华不是结论，是推理路径——面试照这个讲，比背结论高一档：

  1. 数据库索引的目标函数不是"比较次数少"，是"磁盘 IO 次数少"（机械盘一次随机读约 10ms，IO 次数就是命）。
  2. 树高 ≈ IO 次数 → 树必须矮 → 必须 N 叉，不能二叉（100 万节点的二叉树高 20 = 20 次随机 IO，不可接受）。N 就是扇出——一个节点能装多少个"指向下一层的指针"，由页大小决定：InnoDB 一页 16K，每条"键 + 指针"约 14 字节 → N ≈ 1200。容量 = 扇出树高-1 × 每叶子页行数：扇出是指数底数，所以"键越小 → 扇出越大 → 树越矮"——自增 bigint 8 字节对 UUID 36 字节，扇出约 1170 对 390，这是强制自增主键的另一半理由。
  3. N 叉树的两个变体：B 树每个节点都存数据 → 扇出小 → 树更高；B+ 树非叶子只存键 → 扇出拉满 → 更矮，且叶子间链表让范围查询顺着走。
  4. 所以结论不是"B+ 树最好"，而是"按访问模式选结构"——这才是架构师口径。
结构等值查询范围 / 排序树高 / IO致命伤真实用途
哈希表O(1) 最快全废（无序，区间 = 全扫）—只支持等值Redis / Memcached；InnoDB 自适应哈希索引
红黑树O(log N)中序遍历可行但慢log₂(100万) ≈ 20为内存设计：每节点只存一键，吃不满 16K 磁盘页；二叉 → 树高 = IO 次数Java TreeMap、HashMap 树化、epoll——纯内存结构
B 树O(log N)，运气好非叶子提前命中中序回溯，不顺较高非叶子存数据 → 扇出小 → 树更高；范围查询弱现代主流数据库已很少用纯 B 树
B+ 树O(log N)，稳定到叶子叶子双向链表，范围最强3-4 层写入有页分裂成本InnoDB：聚簇索引叶子存整行，二级索引叶子存主键 → 回表（接链 2）
两个容量口径都要会（防追问） 45 讲口径：N ≈ 1200，树高 4 → 1200³ ≈ 17 亿个键，根节点常驻内存，十亿行的表最多 3 次磁盘 IO。链 1 口径：1170 × 1170 × 16（叶子页每行 1K）≈ 2200 万行。两个都对、假设不同：前者算"能定位多少个键"，后者算"聚簇索引能装多少行"。面试任选其一，但把假设说出口——能分清口径的人，面试官立刻知道你不是背的。
