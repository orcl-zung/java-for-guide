★★★ 链 1 · Redis 为什么快？单线程为什么反而快？

一层：四个原因一口气说完——纯内存操作（纳秒级）+ 单线程无锁竞争、无上下文切换 + IO 多路复用（epoll，一个线程看管所有连接）+ 高效数据结构（SDS/跳表/listpack）。

追问①：单线程为什么不是瓶颈？
Redis 的瓶颈在网络 IO 和内存带宽，不在 CPU；单线程免掉了锁竞争和线程切换的开销，反而把内存操作的速度优势吃满。

追问②：6.0 为什么又引入多线程？
多线程只用在网络读写（IO 线程组并行收包/发包），命令执行仍然是单线程——所以无锁设计全部保留，不存在多线程写数据的一致性问题。别答成"6.0 变多线程了"，要说清线程用在了哪。

追问③：单线程的坑是什么？
一条慢命令堵死全服务：keys *、大 key 的 hgetall/smembers、bigkey 的 del。生产对策：禁 keys 用 scan；大 key 删除用 unlink（异步）；监控 slowlog。

你的锚点：被问"你们 Redis 出过什么问题"时，慢命令 + 大 key 是最自然的故障叙事入口（接链 2 追问③）。

★★★ 链 2 · 数据结构：string/hash/zset 底层是什么？场景怎么选？

一层：五件套场景先顺溜——string：计数器、缓存对象（JSON）、分布式锁；hash：对象部分字段频繁改（比 string+JSON 省内存、可单字段改）；list：简单队列；set：去重、交集（共同好友）；zset：排行榜、延迟队列（score=执行时间戳）。

追问①：底层结构？
SDS：O(1) 取长度、二进制安全、预分配减少扩容（对比 C 字符串三宗罪）；hash：listpack（7.0 前 ziplist）→ 阈值后转 hashtable；zset：元素少用 listpack，多了用 skiplist + hashtable（跳表管范围、哈希管单查）。

追问②：zset 为什么用跳表不用红黑树？
三板：范围查询跳表是链表顺序遍历、红黑树要中序遍历；实现简单得多；插入删除不需要旋转平衡。加分回答：跳表层级靠随机，期望 O(logN)。

追问③：大 key 和热 key 怎么处理？
大 key：阻塞单线程（删/读都慢）、内存倾斜（集群里某个节点爆）、迁移慢——拆 key（大 hash 拆成 N 段）、unlink 异步删、能不用大集合就不用。热 key：单节点被打爆——本地缓存（Caffeine）兜一层、热 key 拆多份加随机后缀、读写分离分摊读。

追问④：zset 在你手里还干过什么？——延迟队列 + 滑动窗口限流（你技能清单写了，必被拷）
延迟队列：score = 触发时间戳，zrangebyscore 捞到期的任务；Redisson 延迟队列底层同构（zset 排队 + list 就绪 + 定时搬运），开箱即用。必带选型对比——你 MQ 侧明明写了 TTL + 死信：固定时长的延迟兜底走 MQ 省事，但 TTL 队列"到点必死"，不能随时取消、不能动态改时间；订单超时这类"可能提前取消"的延迟任务走 Redisson（zrem 即取消）。
滑动窗口限流：zadd 时间戳入窗 → zremrangebyscore 清窗外 → zcard 计数，超阈值就拒——三条命令打成一个 Lua 保原子。对比固定计数器的临界突刺：窗口滑起来，边界瞬间就没有双倍流量问题。

你的锚点（话费三结构连发）：简历原话就是场景题答案——Hash 存系统参数（字段级改，比 string+JSON 省内存）、List 管限时支付凭证（FIFO，旧凭证先淘汰）、Set 防订单重复（sadd 判重）。被问"你用过哪些结构"就把这三连甩出去，每个都带场景。追问④两个锚在充电宝：Redisson 延迟队列框架 + 网关滑动窗口限流。

★★★ 链 3 · 穿透 / 击穿 / 雪崩 + 缓存一致性怎么保证？

一层（三兄弟必须一口气顺溜讲完）：穿透＝查根本不存在的数据，缓存永远 miss，请求全打到 DB → 布隆过滤器拦 / 空值缓存（短 TTL）；击穿＝一个热点 key 过期瞬间，并发全回源 → 互斥锁（只放一个请求回源）/ 逻辑过期（不真过期，异步刷新）；雪崩＝大面积 key 同时过期或 Redis 宕机 → 随机 TTL 打散 + 多级缓存 + 限流降级兜底。

追问①：缓存一致性（Cache Aside 旁路缓存）：读——先查缓存，miss 回源 DB 再写缓存；写——先写 DB，再删缓存。两个"为什么是删不是更新"：懒加载避免无效计算（写了不一定有人读）；更新缓存在并发下会双写不一致（两个写线程交叉更新出旧值）。

追问②：先写库还是先删缓存？窗口都在哪？
先删缓存再写库：删完还没写库，另一个线程读 miss 回源拿到旧值写进缓存 → 长时间脏数据。先写库再删缓存：窗口极小（读 miss 回源恰好发生在写库前、删缓存后），但仍存在 → 所以引出延迟双删（写库后隔几百 ms 再删一次）或 binlog 订阅（canal）异步失效兜底。

追问③：能保证强一致吗？
不能，也别保证——缓存的定位就是最终一致。强一致诉求的数据（库存、余额）不要走缓存，走 DB 行锁/乐观锁。这句一出，面试官知道你真权衡过。

你的锚点：充电宝的 Caffeine + Redis 多级缓存（按堆内存自适应上限）——一级 Caffeine 挡热 key（勾连链 2 追问③），二级 Redis，miss 回源 DB；写侧先写库再删 Redis，Caffeine 靠短 TTL 自然过期兜底，接受秒级不一致。口径提醒：延迟双删你只答原理，别 claim 项目里用了——简历没写，被追问就说"评估过，我们时效要求不高，短 TTL 已够"。

★★☆ 链 4 · 持久化 + 高可用：RDB/AOF、主从、哨兵、集群？

一层：RDB＝定时快照，恢复快但丢整个窗口；AOF＝命令追加日志，everysec 最多丢 1 秒；4.0 起混合持久化＝RDB 头 + AOF 增量，鱼和熊掌。高可用三级：主从复制 → 哨兵（监控+自动故障转移）→ 集群（16384 槽分片，gossip 通信）。

追问①：AOF 刷盘策略与 rewrite？
always/everysec/no 三档——和 MySQL innodb_flush_log_at_trx_commit 0/1/2 是同一个"安全 vs 性能"权衡（勾连第 2 课链 6 阅读指南）。rewrite＝把冗余命令压成最小命令集（set a 100 次只留最后一次），fork 子进程做、不阻塞主线程。

追问②：主从复制细节 + 脑裂？
全量（RDB 快照 + 缓冲命令）vs 增量（repl_backlog 环形缓冲区）。脑裂：主库假死，哨兵升从为新主，旧主复活后客户端还往旧主写 → 数据双份。缓解：min-replicas-to-write（旧主写不进从库就拒写）。

追问③：集群为什么是 16384 个槽？
槽位信息靠心跳包广播：65536 个槽的 bitmap 要 8KB/心跳，太浪费；16384 只要 2KB；且集群节点一般不过千，16384 够分。

你的锚点：充电宝出海的 Redis 是哨兵还是集群、为什么这么选——想不起来今晚就去查，这是"你们架构怎么搭的"必答题。

篇目判定读法与理由
① 多节点争抢资源，Redis 分布式锁是怎么实现的？（小林）必读 ★★★主战场，锁四问题演进链：锁争抢 → 僵尸锁（setnx + expire 不原子）→ 锁过期（业务没跑完锁没了）→ 单点（主从切换丢锁）；对应解法 SET NX EX 一条命令 + 唯一 value + Lua 比对释放 + 看门狗续期 + RedLock 多数派。一层答案与追问①全在这
② 如何保证 Redis 分布式锁的高可用和高性能？（小林）必读 ★★★进阶篇，全是追问弹药：加锁失败等待轮询 vs 事件监听、可重试的幂等设计（GET 校验 UUID 三种情况）、锁过期 P999 + 缓冲提前量、看门狗续约失败时保守中断 vs 激进继续、业务中断用 volatile / interrupt 检查点、锁有效时间 = 过期时间 − 加锁耗时、Singleflight / 本地锁交接的批判——追问③"什么时候不该用分布式锁"的另一半弹药（另一半是你 webhook 的 DB CAS）
③ How to do distributed locking（Martin Kleppmann，英文）必读 ★★★追问②争议的一手原文：用锁的两个目的（效率 vs 正确性）、时钟跳变 + GC 停顿让 RedLock 失效的时序图（客户端 1 拿锁 → GC 卡住 → 锁过期 → 客户端 2 拿同一把锁 → 客户端 1 醒来写旧数据）、根治靠 fencing token（单调递增令牌，下游拒绝旧令牌）。面试说出"Kleppmann 的 fencing token"，直接和背八股的分层
④ Is Redlock safe?（antirez，英文）快读 15 分钟反方回应：Redis 作者逐条反驳，分歧核心在时钟模型假设（Kleppmann 假设时钟会跳变，antirez 认为工程上时钟大体可靠）。能讲清"双方分歧点在哪"，比站队任何一方都高级

自测口径：双锚点（货柜选型 + 充电宝双保险）讲完后主动抛 RedLock 之争——"我读过这场争论的原文，Kleppmann 的 fencing token 是根治方案，但我们这个量级 Redisson 看门狗 + DB 行锁兜底已够"。一句把理论、一手文献、工程权衡说齐。

★★★ 链 5 · 分布式锁怎么实现？Redisson 原理？

一层：SET key value NX EX 原子抢锁（NX 不存在才设 + EX 过期，一条命令原子——别拆成 setnx + expire 两条）；value 存唯一标识（UUID/线程 ID），释放用 Lua 脚本"比对再删"（防误删别人的锁）。

追问①：锁过期了业务还没跑完？
Redisson 看门狗：默认锁 30s，后台线程每 10s（1/3）续期，业务活着锁就在；Redisson 加锁失败默认自旋重试 + Lua 保原子。可重入靠 hash 结构（field=线程，value=重入次数）。

追问②：主从切换丢锁？
锁写主库还没同步到从库，主库挂了、从库升主 → 锁没了，第二个人又拿到同一把锁 → RedLock（多数派节点都加成功才算成功）→ 但 RedLock 有争议：Martin Kleppmann vs antirez 之争——时钟跳变、GC 停顿下 RedLock 也不绝对安全，根治要 fencing token（单调递增令牌，下游拒绝旧令牌）。说出这场争论直接加分。

追问③：什么时候不该用分布式锁？
能用 DB 唯一约束/条件更新兜底的场景别上锁——你充电宝 webhook 的简历原话就是"DB CAS 更新而非分布式锁防重扣费"：重复回调天然在 CAS 上撞墙，比锁简单还可靠。分布式锁治"互斥执行"，不包"数据正确性"。

你的锚点（双份，注意项目归属）：①货柜项目——Redisson 锁限制同一货柜并发下单，"为什么选 Redisson 不手写 setnx：看门狗续期 + 可重入 + 现成的 Lua 释放"；②充电宝广告计费——"FOR UPDATE 行锁 + Redisson 分布式锁双保险"：Redisson 在入口挡跨实例并发，行锁是数据正确性的最后防线，两道各管各的。加分补一句：锁在充电宝已沉淀成 SpEL key 注解，业务方法零侵入。

★★★ 链 6 · 场景题：秒杀/限量发放的库存怎么设计？（系统设计专项预演）

一层（三板斧主线）：前端静态化 + CDN 挡读流量 → Redis Lua 预扣库存（原子扣减，扛住洪峰）→ MQ 异步下单削峰 → DB stock > 0 条件更新兜底。讲清一句：DB 不能碰洪峰流量，流量在 Redis 层就要消化掉。

追问①：为什么 Lua？
Redis 单线程执行，脚本整体原子——"查库存 + 扣减"若拆成两条命令，中间会被人插队（check-then-act 的 Redis 版，勾连第 2 课链 4 幻读事故形态）。

追问②：Redis 扣了、DB 没写成怎么办？
MQ 消费失败重试 + 死信队列兜底；定时对账任务核 Redis 与 DB 库存；超卖最终防线是 DB 的条件更新（update ... where stock > 0，靠行锁串行化最后一道）。

追问③（流量大 10 倍）：库存拆段（100 个 key 各存 1/100，扣完再合）、本地缓存读、限流令牌桶、降级（卖完直接返回，不再回源）。

你的锚点（用审计+设计稿口吻，别用主导口吻——简历里寻宝是你的审计对象）：活动引擎的"先到先得"就是秒杀同构。话术："我审计寻宝全链路时定位过发放链路的 14 项缺陷，引擎归位方案里 FirstCome 走 Redis Lua 预减 → MQ 异步落库 → DB 条件更新兜底，红包余量就是库存"——这套第 5 课设计稿写着，code/activity-engine 里有你亲手写的 Lua 片段，讲得有底气。这是你系统设计专项（9/19-20）的第一块积木。
