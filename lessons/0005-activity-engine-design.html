第一章 · 背景两套并存体系的痛点

power-bank 的营销能力散在两套互不相通的体系里——这不是设计，是历史堆积。

发券体系寻宝体系
表ot_coupon / ot_act_base_infoops_activity + ops_treasure_*
状态coupon-refactor 重构后相当完善（锁券/核销/自然日有效期）6 个 Service ≈ 1750 行，任务/决策/库存/发奖四概念纠缠
抽奖SPIN 只是枚举值，RandomDrawRewardStrategy 是 TODO 空壳——真实预留扩展位

coupon-refactor spec 的 Ask First 里挂着一道悬案："是否将优惠券与新的 ops_activity 活动体系合并"。本设计稿就是它的正式回答：不合并，引擎编排 + 领域自治。

30 秒开场白（背到脱口而出）
"Ingoo 的营销能力是两套并存：发券一套、寻宝一套，抽奖只有枚举没有实现。我识别出三类玩法共享同一组概念——资格、任务、决策、库存、发奖——设计了统一活动引擎：五节点管线做内核，玩法做插件，存量券域通过适配层接入。寻宝没有重写，是把旧代码里隐含的概念显式化归位；抽奖内核和决策算法库我做了代码级验证。"

第二章 · 上帝视角行业全景与五维公式

只对着三种玩法设计，出来的是"三种玩法的并集"而不是"玩法之母"。先把业内营销活动的机制家族铺开。

机制家族代表玩法核心差异点
概率类转盘 / 九宫格 / 盲盒 / 刮刮卡决策 = 概率
直发类注册礼 / 首单礼 / 定向发券无决策，触发即给
累积任务类连签 / 邀请N人 / 集卡 / 砍价助力有"进度"，达成才发
竞争类秒杀 / 红包雨 / 拼团先到先得，库存高并发
排名类消费榜 / 邀请榜 / PK 赛决策 = 排名取前 N
场景类LBS 寻宝 / 到店打卡 / AR 集福触发 = 地理位置
交易促销类满减 / 满折 / 加价购嵌交易链路，决策 = 门槛判断

五维公式：所有玩法 = 五个维度的笛卡尔组合

触发方式 × 任务进度 × 决策模式 × 权益类型 × 约束
 触发：主动 / 行为事件(MQ) / 定时 / 地理位置
 任务：无 / 单次 / 累积进度 / 排名竞争（可选维度）
 决策：必中 / 概率 / 概率+保底 / 先到先得 / 排名取前N
 权益：券 / 实物 / 碎片 / 积分 / 现金红包
 约束：库存 / 预算 / 频控 / 人群

验证：砍价 = 事件触发 × 累积进度 × 达成即中 × 免单；秒杀 = 定时触发 × 无任务 × 先到先得 × 商品；寻宝 = 地理位置 × 单次行为 × 必中+概率掉落 × 券/碎片。抽奖、寻宝、发券只是这张表的三行——这就是"通用"的证明方式。

引擎的检验标准
新增一个玩法（签到、砍价），需不需要加表？默认零新表，纯配置组合出玩法；只有存在共享实体或特殊查询模式时才允许私有存储（判据见第五章）。

第三章 · 内核五节点管线 + 玩法插件

触发（双入口：同步 API / MQ 行为事件）
  → ① 资格责任链   装配态 → 风控封禁 → 黑名单 → 人群 → 频控 → 次数账户
  → ②a 任务进度    counter / collection(item_key) / streak（可选节点，空任务直穿）
  → ②b 决策        DecisionStrategy SPI（算法见第四章）
  → ③ 规则树       库存校验 → 兜底奖 → 风控拦截
  → ④ 统一发奖中心  AwardIssuer SPI + 幂等流水

两套"五"的关系：公式是配置空间，管线是运行时内核

第二章的五维公式与本章的五节点管线不是同一个"五"的两种写法：公式回答"一个玩法是什么"（声明式配置空间），管线回答"一次参与怎么执行"（命令式运行时内核）。维度逐个落点：

五维公式（静态配置）五节点管线（动态执行）
触发方式管线入口（同步 API / MQ 双入口）——不是节点
任务进度②a 任务进度节点
决策模式②b 决策 SPI
权益类型④ 发奖中心（每种权益一个 AwardIssuer 实现）
约束 · 人群/频控/次数① 资格链
约束 · 库存/预算③ 规则树

两处"不整齐"正是设计点。约束拆两半：人群/频控是便宜的读，尽早短路（被挡的请求不配消耗下游算力）；库存/预算必须等 ②b 选出具体奖品后才能扣——得先知道扣哪个奖品的库存，兜底奖也只能长在决策之后。触发没有节点：它决定谁调用管线、要不要同步等结果，发生在管线开始之前（触发方式决定返回时效，不是反过来）。一句话收口：公式管组合自由（维度正交随便乘），管线管执行收敛（顺序、幂等、成本定序只有一份）——N 个玩法 = N 行配置，全流进同一条管线，笛卡尔积不产生代码爆炸。

① 资格链：成本升序 + 短路，两公理定序

#节点数据源成本
0活动装配态（状态/时间）装配缓存（内存）O(1) 读
1风控封禁Redis GET读
2黑名单Redis SISMEMBER读
3人群/归属（新老人/商户）Redis / 本地缓存读
4频控（日/总次数）Redis INCR第一个写
5次数账户扣减DB 条件更新最贵的写，压尾

公理一：读前写后——前置拒绝不产生写副作用（被黑名单挡掉的请求不该留下频控计数）。公理二：便宜先贵后——DB 写压到最后一跳，此时请求已确认合法。追问预演："风控为什么排在黑名单前？"——黑名单是静态运营配置，风控是动态攻击信号，攻击信号优先于业务规则，越早挡越省下游算力。

②a 任务进度：三种进度语义覆盖累积家族

语义玩法实例存储
counter邀请 N 人 / 消费 N 次activity_progress 单行计数
collection集卡 / 碎片（每碎片一行）+ item_key 维度
streak连续签到（断签重置策略入参）current_streak + last_date

PRD 的 N（距上次中奖次数）也存在这张表里——五维模型内部自洽。进度达成即触发 ②b 决策；任务达成还可以反向给次数账户充值（邀请得抽奖次数），账户闭环。

②b 决策 SPI 与 ④ 发奖中心 SPI

决策实现玩法发奖实现权益
MustHitDecision发券 / 签到 / 砍价达成CouponAwardIssuer券（委托 ot_coupon 域）
WeightedTableDecision抽奖主力FragmentAwardIssuer碎片（通用进度表）
PrdPityDecision稀有掉落 / 高价值奖品GrandPrizeAwardIssuer实物（待核销流）
LuckyMoneyDecision红包（v1 只设计）扩展位：实现接口即接入
FirstComeDecision秒杀 / 限量（委托③库存节点）

存量整合纪律：发奖中心只管"给谁发、发什么、发没发成"（幂等、库存、落账）；券怎么用（锁券/核销/满减计算）留在 coupon 域——引擎编排 + 领域自治，限界上下文划清。

触发双入口

同步入口 POST /activity/{id}/participate：主动参与（抽奖/打卡/领券），走完整管线同步返回（转盘动画要等结果）。异步入口 MQ 行为事件：注册/首单/登录/支付，按活动 trigger_type 匹配后走管线，结果落库 + 站内通知。为什么不全事件总线？触发方式决定返回时效，不是反过来——同步需求硬塞异步模型是"为了统一而统一"。GEO 附近查询是"活动发现"层，不进管线（管线从用户点击开始）。

第四章 · 算法决策算法库（代码切片验证）

每个算法带分布统计测试——"我不仅实现了，还用统计测试验证过分布正确性"。

4.1 加权区间查表（抽奖主力，P0）

装配期：权重（百万分比整数，杜绝浮点）展开成 [0, 1_000_000) 区间
        小池(≤64奖品) → O(1) 数组直查：下标即随机数
        大池/高精度   → O(log N) CDF 二分（upper_bound 语义）
运行期：一次随机 + 一次查表（随机数只生成一次——循环内重复生成破坏分布）
库存联动：③扣库存失败 → 该奖品区间置空 + 剩余权重归一化重建

为什么不用 Alias（O(1) 严格均匀）：Alias 采样 O(1) 但构建 O(N) 且概率变更需全量重建两张表；营销抽奖库存实时消耗、概率频变，区间查表改边界即可。Alias 适合概率静态的游戏卡池，不适合库存驱动的营销抽奖。知道但主动不选 > 只会加权随机。

4.2 PRD 伪随机 + 硬保底（稀有掉落，P0）

P(N) = C × N     N = 距上次命中次数，命中重置
C 由标称概率二分反解（对照表：25%→C≈8.5%→保底12次；15%→3.2%→32；50%→30%→4）
期望与真随机相同，方差收窄——消灭欧皇连中与酋长连空
硬保底是 PRD 的自然推论：N = ⌈1/C⌉ 时 P = 1 必中
N 存 activity_progress（五维模型自洽点）

落地场景：寻宝稀有碎片掉落。"真随机对用户体验是灾难"——这是把 PRD 引进引擎的业务理由，不是炫技。

4.3 二倍均值法（拼手气红包，P1）

剩余 M 分、剩 N 人：本次金额 ∈ [1分, (M/N)×2] 均匀随机，最后一人拿剩余
期望恒 = 当前剩余人均 → 先抢后抢数学公平（微信同款）
对比线段切分法：理论更随机但方差失控（0.01 vs 99.99 极端值），业界弃用
铁律：全程"分"为单位 long 运算，禁止浮点金额

4.4 先到先得（秒杀，P2 片段）

先到先得拼的不是算法是漏斗——每层过滤一个数量级：
CDN 静态化 → 网关限流/答题 → 令牌桶 → Redis Lua 预减 → MQ 异步落库 → DB 条件更新兜底
切片：resources/seckill/pre_deduct.lua（SISMEMBER 幂等 + DECR 预减，原子）
纪律：Redis 只是削峰，最终一致性 = DB stock>0 条件更新 + 超时未支付回补 + 定时对账
切片验收标准（code/activity-engine/，11 个 @Disabled 待点亮）
加权/PRD：10 万+ 次采样，频率误差 ≤ ±5%；PRD 加断最大连空 = 保底次数；红包：总额守恒分毫不差 + 各位置期望公平；PRD 多用户计数隔离。

私有存储判据：默认零新表，两种例外

例外玩法私有存储原因
共享实体（非"用户×活动"标量状态）寻宝 / 拼团 / 一番赏宝箱实例表 / 团表 / 箱表宝箱=带独立状态机的持有容器；团=多用户共享实体
特殊查询（通用索引做不了）寻宝 / 排行 / 秒杀Redis GEO / ZSET / 预减 key半径搜索、实时排名、高并发预减——多为 Redis 结构而非 DB 表

签到/邀请/砍价/抽奖/发券/满减全部能用三张通用账户 + 配置表组合出来——这是引擎敢叫"引擎"的原因。反面教材：旧寻宝 startTaskParam 设计成 JSON 实存裸数字（parseInviteRequired 的 try-catch 是事故现场），所以配置列拒绝 JSON 大字段，维度即表。

装配：配置流与状态流分离

活动发布/编辑/下架时把配置组装成运行态对象（概率区间表、资格参数、任务定义）写入 Redis，变更发 MQ 事件驱动重装（秒级生效）；运行中库存/次数等状态变化只改 Redis 计数不回装。装配期做概率和校验（权重和必须 = 1,000,000，"谢谢参与"补足）。

第六章 · 一致性双通道 + 幂等键 + 补偿三段

双通道按玩法路由：决策 SPI 声明一致性级别

通道决策机制适用量级
同步事务通道MustHit / Weighted / PRDDB 条件更新扣库存 + 流水 insert + 账户扣减，同一事务营销常规（日均万级）
异步通道FirstComeRedis Lua 预减 → MQ 异步落库 → DB 条件更新兜底秒杀/红包雨洪峰

两条通道的共同最终防线都是 DB 条件更新——"Redis 可用于削峰和用户体验锁，但不是最终一致性依据"（coupon-refactor spec 已定原则的引擎化泛化）。引擎不是给所有玩法套同一套一致性，而是让玩法按量级自选通道。

幂等键与补偿

  • 幂等键：activityId + userId + bizKey 唯一约束（抽奖 bizKey=第 N 次序号；行为事件 bizKey=behaviorKey；手动领取 bizKey=clientRequestId）——重复请求、MQ 重投、客户端重试全被一个索引挡住。
  • 补偿三段：①同事务回滚解决"扣了库存没写成流水"；②MQ 通知失败走本地消息表重投（嘉立创三表组件经验）；③超时未使用权益定时释放（coupon 锁券释放同款）。
  • 对账：定时任务重算"发放计数 vs 流水"，差异告警。
  • 次数语义：参与即扣（业内双维度实证：参与次数与中奖上限是两个独立配置），未中不退走兜底奖；系统异常同事务回滚自然退还。
